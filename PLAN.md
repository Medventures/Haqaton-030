# План реализации AqylRoute MVP

Дата: 30.09.2026. Основа: требования КМУ и спецификации в `.archcore/`.
Это план работ; перечисленные ниже возможности пока не реализованы.
Срок демонстрации и состав команды не заданы, поэтому этапы упорядочены по зависимостям, без календарных обещаний.

## Результат

По публичной HTTPS-ссылке доступны два синтетических кейса. Родитель проходит 8–12 адаптивных вопросов, получает статус ожидания проверки. Куратор видит черновик, редактирует его в рамках справочника и утверждает. После утверждения родитель видит маршрут. Изменения сохраняются после перезагрузки. Просрочка видна семье и в очереди куратора, даже если OpenAI недоступен.

## Архитектура для реализации

```text
Браузер → HTTPS → Next.js на Vercel
                  ├── Route Handlers: проверка доступа, интервью, планы
                  ├── OpenAI Responses API: выбор вопросов и действий
                  └── Облачный Supabase: Auth, Postgres, RLS, история

Route Handler → задание генерации в Supabase → after(): OpenAI → сохранение плана
Зависшее задание (истекла lease) → повторно берётся при следующем запросе состояния или Vercel Cron
pg_cron в Supabase → пересчёт просрочки → уведомления в Supabase
```

- Next.js App Router + TypeScript: интерфейс и сервер в одном приложении.
- Supabase Auth + Postgres: используем существующую основу с ролями `parent` и `curator`.
- OpenAI Structured Outputs: модель возвращает только ограниченную структуру; сервер проверяет содержание.
- Деплой: Vercel (решено 30.09.2026 вместо VPS). Отдельного worker нет: генерация выполняется в `after()` Route Handler с `maxDuration`, восстановление — по lease. Периодическая задача сроков — `pg_cron` в Supabase, потому что Vercel Cron на тарифе Hobby запускается не чаще раза в сутки.
- Supabase остаётся облачным. Миграции применяются через `POSTGRES_URL_NON_POOLING` (psql) из `.env.local`.
- Демо работает на синтетических данных с двумя тестовыми ролями и записью изменений. Назначение роли куратора выполняется администратором, а не переключателем роли в обычном интерфейсе.

Минимальные поля таблиц:

| Таблица | Поля и ограничения |
| --- | --- |
| `profiles` | `id → auth.users`, `role`, `full_name`, `created_at`; роль меняет только администратор |
| `cases` | `id`, `parent_id`, `curator_id`, `workflow_state`, `is_synthetic`, `created_at`, `updated_at`; принадлежность меняется только разрешённой административной операцией |
| `interview_sessions` | `id`, `case_id`, `status`, `answers_json`, `question_history_json`, `question_bank_version`, `revision`, `completed_at`; одна активная сессия на кейс |
| `service_catalog` | `action_id`, `catalog_version`, `definition_json`, `effective_from`, `effective_to`; уникальная пара ID/версия, опубликованная версия неизменяема |
| `case_plans` | `id`, `case_id`, `plan_json`, `schema_version`, `catalog_version`, `revision`, `approved_at`, `approved_by`; один текущий план на кейс |
| `case_events` | `id`, `case_id`, `plan_id`, `actor_id`, `event_type`, `payload_json`, `created_at`; append-only, сервер устанавливает actor/time |
| `notifications` | `id`, `case_id`, `step_id`, `recipient_id`, `event_key`, `type`, `created_at`, `read_at`, `resolved_at`; уникальный `event_key` для события и получателя |
| `generation_jobs` | `id`, `case_id`, `interview_revision`, `base_plan_revision`, `request_key`, `status`, `attempts`, `lease_until`, `error_code`, `created_at`, `finished_at`; уникальность операции и максимум одна активная генерация на кейс |

Индексы: кейсы по `parent_id` и `curator_id`; события по `case_id/created_at`; непрочитанные уведомления по получателю; задания по `status/lease_until`. Отдельную таблицу шагов в первом релизе не вводить: их источник — `plan_json`.

Инварианты:

- В JSON нет `diagnosis`. Каждый шаг содержит все поля принятой спецификации.
- У шагов уникальные `step_id`; `action_id` существует в закреплённой версии каталога.
- `depends_on` ссылается на существующие шаги; циклы запрещены.
- Состояние в колонках для поиска и в JSON согласуется одной операцией БД; клиент не меняет их отдельно.
- Правки интервью после завершения не меняют незаметно уже запущенную генерацию: задание закрепляет ревизию ответов.
- Утверждение привязано к конкретному содержимому плана. Последующие изменения исполнения увеличивают ревизию, но не переписывают первоначальную запись утверждения.
- Добавление/удаление действий после утверждения требует нового цикла проверки; в первом релизе этот сценарий закрыт.

Состояния разных сущностей не смешивать:

| Сущность | Состояния первого релиза | Значение |
| --- | --- | --- |
| Интервью | `in_progress`, `completed` | Отвечает, можно ли менять ответы |
| Задание генерации | `queued`, `running`, `succeeded`, `failed` | Описывает работу генерации, а не готовность плана для семьи |
| Кейс / `workflow_state` | `interview_in_progress`, `generating`, `generation_failed`, `pending_curator`, `returned_for_revision`, `approved` | Краткое безопасное состояние для кабинетов |
| План / `plan_status` | `pending_curator`, `returned_for_revision`, `approved` | План существует только после валидной сборки либо явного создания куратором |
| Шаг | Статусы принятой спецификации | Описывает исполнение одного действия |

Обработчик генерации переводит кейс в `pending_curator` только одновременно с сохранением валидного плана. Неудача генерации сохраняет интервью и переводит кейс в `generation_failed`, без создания фиктивного готового плана.

Проект правил для устранения открытых вопросов:

- Шаг с удовлетворимым prerequisite сохранять как `blocked` с явной зависимостью; действие без необходимого правового/eligibility-основания исключать из допустимого набора.
- Направления и результаты подтверждает куратор через структурированные поля, без загрузки документов. Сам текст объяснения AI не устанавливает основания.
- Возвращённый на доработку план правит куратор либо запускает явную повторную генерацию. Родителю показывать ожидание проверки, без черновика.
- Закрытие просрочки не является отдельным произвольным флагом: нужен завершённый/отменённый шаг либо подтверждённое исправление фактической даты. Официальный срок нельзя переносить только для удаления красной метки.
- Состояние плана `closed` оставить в контракте, но не вводить пользовательскую операцию закрытия кейса в первом релизе; отдельно определить доступ к архиву перед её реализацией.

Приёмка DATA: миграции применяются на пустом проекте; нарушающие связи/версии/ревизии операции отклоняются; fixtures A/B валидны; отменённая транзакция не оставляет половину изменения.

### 5. Серверные API и операции

Предлагаемые endpoints; все изменения идут через серверную валидацию. Внутренние функции домена не зависят от HTTP, чтобы их можно было проверять отдельно.

| Метод и путь | Назначение | Вход | Ответ/ограничения |
| --- | --- | --- | --- |
| `POST /api/cases` | Создать собственный кейс | Минимальный контекст | ID кейса; parent определяется сессией |
| `GET /api/cases` | Список доступных кейсов | Фильтры, cursor, limit | Только разрешённые краткие поля |
| `GET /api/cases/[id]` | Состояние кейса | ID | Состояние обработки и доступный summary |
| `GET /api/cases/[id]/interview` | Продолжить интервью | ID | Текущий вопрос, сохранённые ответы, revision |
| `POST /api/cases/[id]/interview/answers` | Сохранить ответ и выбрать следующий вопрос | `question_id`, типизированный ответ, `expected_revision` | Подтверждённая ревизия и следующий вопрос |
| `POST /api/cases/[id]/interview/complete` | Проверить завершённость и начать генерацию | Ревизия, ключ операции | `202` и ID задания; повтор не создаёт новое |
| `GET /api/cases/[id]/generation` | Узнать состояние задания | ID | `queued/running/succeeded/failed`, безопасный error code |
| `POST /api/cases/[id]/generation/retry` | Повторить неудачную генерацию | Ревизия, ключ операции | `202`; запрет при активном задании/утверждённом плане |
| `GET /api/cases/[id]/plan` | Получить доступную версию | ID | Родителю только утверждённый план; куратору допустим черновик |
| `PATCH /api/cases/[id]/plan/draft` | Отредактировать черновик | Ограниченные операции, expected_revision | Куратор; полный валидатор после правки |
| `POST /api/cases/[id]/plan/approve` | Утвердить ревизию | expected_revision, ключ операции | Атомарное утверждение и событие |
| `POST /api/cases/[id]/plan/return` | Вернуть на доработку | expected_revision, структурированная причина | Только до утверждения, семье черновик не виден |
| `PATCH /api/cases/[id]/steps/[stepId]` | Обновить исполнение | Разрешённый статус/дата/результат, expected_revision | Проверка роли, перехода, prerequisites; JSON + event |
| `GET /api/curator/overdue` | Получить очередь просрочек | Фильтры, pagination | Только назначенные кейсы |
| `GET /api/notifications` | Собственные уведомления | Pagination | Только текущий recipient |
| `PATCH /api/notifications/[id]` | Отметить прочитанным | Разрешённое изменение | Не меняет срок/статус шага |
| `GET /api/health` | Проверить процесс | — | Без конфигурации, ключей и сведений о пользователях |

Общий формат ошибки: `code`, безопасный `message`, `request_id`. Семантика: `400` — неправильный ввод, `401` — нет сессии, `403` — запрещённая операция, `404` — отсутствующий или чужой кейс, `409` — конфликт ревизии/состояния, `429` — лимит, `503` — сервис временно недоступен. Внутренний stack trace клиенту не отдавать.

Транзакция смены статуса: прочитать доступный план с блокировкой → сверить ревизию → проверить переход → изменить конкретный шаг → пересчитать зависимости/сроки → увеличить ревизию → добавить событие → commit. При ошибке любое изменение отменяется.

Транзакция утверждения: проверить назначенного куратора и ревизию → повторно валидировать план → проверить наличие шагов → зафиксировать snapshot утверждения в событии → записать approval в JSON/колонки → изменить состояние кейса → commit. Повтор с тем же ключом возвращает уже выполненный результат.

| AI-06 | Настроить лимиты, ошибки и ручной путь | Нет бесконечных повторов и скрытых дублей | AI-02, AI-05 |

Темы банка: возраст, регион, главная задача, обращения в здравоохранение, ранняя помощь, образование, ПМПК, школьная поддержка, соцподдержка, наличие документов, поданные заявления/результаты/даты, препятствия. Банк может содержать больше 12 вопросов; в конкретной сессии задаётся 8–12. Условные вопросы не должны вытеснять обязательные темы и делать минимум недостижимым.

Сервер определяет применимость вопросов; модель выбирает очередной ID из оставшихся. Временные значения и флаги сохраняются в типизированном виде. При нехватке применимых вопросов — добавить заранее спроектированные нейтральные вопросы об организации маршрута, а не повторять вопрос и не придумывать медицинский опросник на лету.

Модель для плана получает: возрастную группу, регион, этап образования, цели из списка, факты/флаги маршрута и допустимые действия. Она не получает email пользователя, ID аккаунта, ФИО, адрес, документы или контакт куратора. Промпт и схемы версионировать; в событии генерации хранить версии, имя модели и итог проверки, без полного чувствительного содержимого.

Проверка текста объяснения включает ограничения длины, запрещённые диагностические формулировки и тестовый набор негативных примеров. Она не является доказательством отсутствия любых содержательных ошибок: окончательную проверку выполняет куратор. Для отклонённого текста допустим повтор в пределах общего лимита либо объяснение из заранее проверенного шаблона каталога с явной отметкой происхождения.

Конвейер генерации:

1. Проверить завершённость интервью и право пользователя.
2. Создать задание, закрепить ревизию ответов и версию каталога.
3. Обработчик в `after()` забирает задание с временной lease; другой вызов не выполняет его одновременно. Задание с истёкшей lease повторно берёт запрос состояния генерации или cron-endpoint.
4. Вычислить допустимые действия; при пустом наборе вернуть явную ошибку для ручной проверки, не сохранять пустой «готовый» план.
5. Запросить Structured Output, обработать refusal, таймаут, неполный ответ и ошибку API.
6. Проверить действия и текст; достроить план из каталога; выполнить полный валидатор.
7. В короткой транзакции сверить актуальность задания, сохранить план, событие и `pending_curator`.
8. При провале записать безопасный код ошибки; интерфейс предлагает повтор или путь к куратору.

Стартовые параметры для настройки на двух кейсах: не более двух вызовов генерации на одно задание, до 60 секунд на отдельный вызов плана, до 10 секунд на выбор вопроса. Это рабочие значения для измерения, а не гарантии внешнего API. Повторы транспортной ошибки и исправления ответа имеют общий предел; SDK-ретраи учитывать, чтобы не умножить вызовы незаметно.

Состояния задания: `queued → running → succeeded/failed`. Lease истекла после сбоя — задача может быть повторно взята в пределах лимита. Просроченный результат прежнего вызова не перезаписывает новый: перед сохранением проверять владение lease/attempt и актуальность задания. Из-за сетевых сбоев повторный платный вызов возможен; гарантировать отсутствие дубликатов в собственной БД, не обещать exactly-once для внешнего API.

Во время `generating` изменение завершённых ответов и запуск второго задания запрещены. Повторная генерация черновика — явная операция куратора с проверкой ревизии; утверждённый план не заменяется ответом модели.

Родитель после завершения видит сначала «Подготавливаем маршрут», после успешного сохранения — «Ваш маршрут готовится к проверке куратором», при отказе — понятную ошибку. Не смешивать состояние задания с `plan_status`.

### 7. Статусы, сроки и уведомления

Проект переходов для уточнения DATA-01:

| Исходное состояние | Действие | Новое состояние | Кто |
| --- | --- | --- | --- |
| `draft` | Утвердить план и проверить условия | `ready` или `blocked` | Сервер по действию куратора |
| `blocked` | Подтверждены все необходимые условия | `ready` | Сервер по подтверждению куратора |
| `ready` | Зафиксировать подачу с датой | `submitted` | Родитель для семейного шага / куратор |
| `submitted` | Зафиксировать ожидание результата | `waiting_external` | Куратор |
| `submitted` / `waiting_external` | Назначить подтверждённую дату | `scheduled` | Куратор |
| `ready` / `scheduled` | Зафиксировать начало исполнения | `in_progress` | Куратор |
| Активный шаг | Подтвердить результат | `completed` | Куратор; родителю только для явно самостоятельного действия |
| Активный шаг | Отменить с причиной | `cancelled` | Куратор |

Это whitelist, а не произвольный выбор enum. Остальные переходы требуют отдельного правила. `completed/cancelled` не открывать обратно в первом MVP; ошибка исправляется отдельной административной процедурой с историей. Если prerequisite завершён, но нужное подтверждение отсутствует, зависимый шаг остаётся заблокированным.

Под активными шагами для завершения понимать `ready`, `submitted`, `scheduled`, `in_progress`, `waiting_external`; `blocked/draft` нельзя завершить в обход проверки условий. Отмену заблокированного шага куратором разрешать отдельно с причиной.

| ID | Задача | Результат | Зависит от |
| --- | --- | --- | --- |
| TIME-01 | Уточнить триггеры и календарь | Проверенные правила, версия календаря, единицы расчёта | DATA-01–03 |
| TIME-02 | Реализовать расчёт времени | Чистые функции с передаваемым `now`, переходы около полуночи/праздников | TIME-01 |
| TIME-03 | Реализовать очередь и создание уведомлений | Идемпотентная задача и актуальные ответы API | TIME-02, DATA-05 |
| TIME-04 | Встроить отображение и разрешение просрочки | Одинаковые метки для обеих ролей, правдивый статус уведомления | TIME-03, UI-04 |

Правила времени: хранить timestamp в UTC, календарный день считать в `Asia/Almaty`. Для date-only срока определить конец локального дня; просрочка начинается строго после `due_at`. До начала триггера `due_at` отсутствует, метки просрочки нет. Для рабочих дней учитывать выходные, праздники и переносы проверенного календаря; интервал услуги и нормативный срок не смешивать.

Число дней просрочки определить как разницу локальных календарных дат, отдельно от булевой метки: сразу после точного `due_at` шаг может быть просрочен менее суток. Для такого случая показывать «Просрочено менее дня», не противоречащие друг другу «просрочено / 0 дней».

Фоновая задача выбирает утверждённые активные планы, рассчитывает просрочку, записывает новое событие и уведомление одной транзакцией. `event_key` включает кейс, шаг, recipient и версию основания срока. При смене куратора уведомление адресуется новому назначенному куратору; прошлое не раскрывает ему лишние кейсы.

Завершение шага разрешает активное уведомление; отметить уведомление прочитанным не закрывает просрочку. Периодический проход сроков выполняет `pg_cron` в Supabase (SQL-функция), независимо от генерации и OpenAI. Функция использует те же правила, что и TypeScript-модуль сроков; их совпадение проверяется тестом.

### 8. Демонстрация и тестовые данные

- DEMO-01: создать отдельные тестовые аккаунты родителя A, родителя B, назначенного куратора и неназначенного куратора для проверки изоляции.
- DEMO-02: подготовить case A без плана и набор ответов для полного интервью; известен ожидаемый допустимый набор действий, но не фиксированный текст модели.
- DEMO-03: подготовить case B с утверждённым планом и прошедшим сроком; источник и тип срока подписаны честно.

Публичный домен ведёт на landing и вход в демонстрационные аккаунты. В MVP не выдавать каждому анонимному посетителю автоматический доступ к привилегированному аккаунту. Если нужен свободный просмотр для жюри без входа, дополнительно сделать read-only синтетическую витрину; она не заменяет записываемый сценарий с проверкой ролей.

| QA-04 | Сквозной путь | Интервью A, утверждение, сохранение статуса; просрочка B | Работает в независимых сессиях и после reload |
| QA-05 | Надёжность | Закрыть вкладку, прервать генерацию, повторить запрос, просрочить lease | Состояние восстанавливается, нет дублей собственных записей |

В CI использовать контролируемые ответы AI, чтобы тесты не зависели от модели и не тратили бюджет. Отдельно выполнить ограниченный живой smoke-test OpenAI на обоих кейсах перед выпуском. Интеграционные тесты БД запускать на выделенной тестовой базе, не на демонстрационных данных.

### 10. Vercel и эксплуатация

| ID | Задача | Проверка результата |
| --- | --- | --- |
| OPS-01 | Создать проект Vercel, подключить репозиторий, дать доступ команде | Preview- и production-деплой собираются |
| OPS-02 | Настроить переменные окружения по окружениям | Публичные Supabase-переменные доступны при сборке, секреты только серверные |
| OPS-03 | Настроить `maxDuration` для генерации и cron-endpoint восстановления заданий | Генерация укладывается в лимит тарифа; endpoint требует `CRON_SECRET` |
| OPS-04 | Настроить `pg_cron` для прохода сроков | Уведомления появляются без открытия страниц |
| OPS-05 | Настроить Supabase Site URL и redirect URL | Вход/подтверждение email возвращает на правильный домен |
| OPS-06 | Логи и наблюдение | Ошибки и исходы генерации видны в логах Vercel без содержимого интервью |
| OPS-07 | Описать резервное копирование и откат | Известен источник бэкапа, откат через предыдущий деплой Vercel |
| OPS-08 | Выпустить и проверить два кейса | QA-06 проходит по публичной ссылке |

Топология: Next.js на Vercel без собственного состояния; Supabase хранит всё. Генерация запускается в `after()` после ответа `202`, поэтому закрытие вкладки её не отменяет; обрыв функции восстанавливается через lease. Длительность генерации ограничена `maxDuration` тарифа Vercel — замерить на двух кейсах.

Endpoint liveness проверяет процесс; readiness отражает доступ к БД без выдачи деталей наружу. OpenAI не является условием liveness.

Минимальные показатели: ошибки HTTP, длительность/исход генерации, задания с истёкшей lease, время последнего прохода `pg_cron`. Логи связываются по `request_id/job_id`, без текстов интервью и API keys.

Порядок выпуска:

1. Пройти CI и репетицию на тестовых данных в preview-деплое.
2. Проверить резервную копию и совместимость миграций с текущей версией приложения.
3. Применить совместимые миграции, не удаляя нужные работающему релизу поля.
4. Выпустить production-деплой; проверить readiness, вход, один путь A и просрочку B.
5. При провале вернуть предыдущий деплой (Instant Rollback); откат приложения не равен откату БД.

### 11. Порядок выполнения и контрольные точки

| Контрольная точка | Входящие задачи | Что можно показать |
| --- | --- | --- |
| M1: доступный стенд | ENV-01–05, OPS-01–02 | Приложение по HTTPS, внешние сервисы подключаемы |
| M2: защищённая база | DATA-01–05, AUTH-01–04, QA-02 | Две роли, миграции, изоляция кейсов |
| M3: полный путь без AI | UI-01–04, fixtures A/B | Сохраняемое интервью, утверждение, маршрут, статусы |
| M4: настоящий AI | AI-01–06, QA-03/05 | Адаптивные вопросы и проверяемый черновик OpenAI |
| M5: сроки и эскалация | TIME-01–04, UI-05 | Просрочка у обеих ролей, уведомление куратора |
| M6: готовое демо | DEMO-01–05, QA-01–06, OPS-03–08 | Вся цепочка по публичной ссылке после перезапуска |

Не переходить от M3 к оформлению дополнительных экранов, пока не подтверждено сохранение данных и утверждение. Справочник и нормативные источники готовить с начала работы, чтобы AI не блокировался отсутствием допустимых действий. Первое размещение на Vercel выполнять рано; финальные проверки идут после функциональных этапов.

После уточнения даты демонстрации и состава команды назначить владельцев задач и сроки контрольных точек. Если времени мало, сокращать декоративные элементы, регистрацию и дополнительные фильтры; сохранять обязательную цепочку КМУ, две роли, проверку куратора, сохранение и просрочку.

### 12. Что считать завершённой задачей

- Изменение соответствует требованиям КМУ и обновлённой спецификации.
- Есть рабочий пользовательский сценарий и проверка его критических ограничений.
- Ошибки и повторные запросы не оставляют скрыто сломанное состояние.
- Проверено сохранение после reload, а для фоновых работ — после restart.
- Новый endpoint/миграция/переменная описаны в документации.
- Нет незаполненных обязательных полей, закоммиченных секретов или временного обхода авторизации в production.
- Результат воспроизводим другим участником команды по README.
